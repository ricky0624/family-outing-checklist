# 親子出門小幫手｜需求規格書

* 專案英文名稱：Family Outing Checklist
* 文件版本：v0.1（Step 01 需求基線）
* 日期：2026-10-30
* 目標：完成一個可公開部署、具備帳號驗證與家庭成員共同編輯功能的小型 Web 專案。
* 狀態：需求基線（F05 採用「主動開始新一次準備才重設」的建議方案）；詳細 UI 與資料表設計留待後續階段。

## 1\. 背景與核心需求

家長帶小孩出門時，需要反覆準備用品。家庭成員希望用手機或電腦共同查看、編輯同一份出門清單，避免漏帶或重複準備。

**核心需求**：使用者可建立空白或固定範本清單，將清單分享給另一位已登入成員。雙方在網路正常且網頁開啟時，能不重新整理而看到彼此的變更；重新進入網頁時則讀取雲端最新資料。

## 2\. 角色與存取規則

* **清單建立者（Owner）**：建立與查看清單、增刪與勾選物品、開始新一次準備、產生邀請碼，以及刪除整份清單。
* **受邀成員（Member）**：加入並查看獲授權的清單、增刪與勾選物品、開始新一次準備；第一版不得刪除整份共享清單。
* **非成員／未登入者**：不得查看或修改私人清單資料。

共享權限由資料庫端驗證，不得只依靠前端隱藏按鈕。使用者須先登入，再使用經伺服端驗證、不可輕易猜測的一次性邀請碼加入清單。邀請碼實際的失效方式與實作細節於資料庫設計階段確定。

## 3\. 第一版範圍（MVP）

|編號|功能|詳細規格|
|-|-|-|
|F01|帳號登入|Email／密碼註冊、登入、登出；登入後取得自己的清單|
|F02|建立清單|可建立空白清單，或從公園／餐廳／過夜旅行三種固定範本建立；範本物品建立後為獨立資料，可編輯|
|F03|物品管理|在有權限的清單內新增、刪除物品；空白物品名稱不可新增|
|F04|勾選物品|每項物品可設為已完成／未完成，完成進度即時更新並儲存|
|F05|新一次準備|使用者主動按下「開始新一次準備」並確認後，將該清單的物品改成未完成；重新開啟網頁不自動重設|
|F06|共享清單|Owner 可產生邀請碼，其他已登入帳號可加入；只有成員能讀寫清單|
|F07|即時同步|同一清單的兩個線上裝置可自動看到新增、刪除、勾選、重設與清單被刪除等變更|
|F08|跨裝置與 RWD|手機與電腦可操作；從任一裝置重新開啟時讀取雲端最新狀態|
|F09|刪除清單|只有 Owner 可刪除；需確認；清單刪除後任何成員均不得繼續使用或新增其物品|

第一版暫不支援：自訂範本、物品照片、AI 推薦、推播、離線寫入／離線同步、修改紀錄、完整衝突合併、帳號管理後台。

## 4\. 操作流程

1. 使用者註冊／登入。
2. 建立空白清單或選擇固定範本，輸入／確認清單名稱。
3. Owner 可取得邀請碼，另一位已登入使用者使用邀請碼加入。
4. 雙方查看同一份清單，新增、刪除、勾選物品；自動取得另一方的變更。
5. 下次出門時，由成員主動觸發「開始新一次準備」，保留物品、重設勾選。
6. 如果 Owner 刪除清單，其他正在查看的成員收到提示並返回清單列表。

## 5\. 業務規則

* R01：建立清單時名稱不得為空，僅包含空白字元亦視為空。
* R02：第一版範本固定為「公園」「餐廳」「過夜旅行」；範本新增為清單後，使用者可以自由新增或刪除物品，原始範本不受影響。
* R03：取消建立時，不得產生清單資料。
* R04：勾選與取消勾選應明確寫入 `已完成=true/false`，避免將同一個狀態重複「反轉」。
* R05：不同物品的更新應各自保留；同一筆物品若有相反更新，以資料庫最後**成功寫入**的值為準，所有裝置最後應呈現相同結果。
* R06：重新整理或重新進入清單時，不得重設勾選；只有使用者主動開始新一次準備才重設。
* R07：若清單已被刪除，任何尚未完成的修改都不能讓已刪清單恢復或產生孤立物品。
* R08：儲存失敗時不可顯示「已成功儲存」；需顯示適當提示並允許使用者重新取得最新狀態。
* R09：Owner 才能刪除整份清單；Member 只管理清單中的物品。
* R10：非成員無權存取他人的清單、物品與共享資訊；包含直接呼叫資料 API 的情況。

## 6\. 驗收測試

### F02 — 建立清單

|測試編號|操作|預期結果|
|-|-|-|
|F02-T01|選擇空白清單，輸入「公園」並建立|新增名稱為「公園」、沒有物品的清單|
|F02-T02|選擇「公園」範本並建立|建立清單並產生預設物品；可新增或刪除個別物品，不影響系統範本|
|F02-T03|輸入資料後按「返回」或「取消」|返回前一畫面，不新增任何清單|
|F02-T04|清單名稱為空，按建立|不得建立；顯示驗證提示|
|F02-T05|清單名稱僅有空白字元，按建立|不得建立；顯示驗證提示|
|F02-T06|建立完成後重新整理|清單仍存在，內容來自雲端資料庫|

### F03 / F04 / F05 — 物品管理與重設

|測試編號|操作|預期結果|
|-|-|-|
|F03-T01|在空白清單新增「尿布」|清單顯示「尿布」，重新整理後仍存在|
|F03-T02|輸入空白物品名稱|不新增物品，顯示提示|
|F03-T03|刪除物品|該物品消失，完成數量正確更新|
|F04-T01|勾選未完成物品|變為已完成，完成數量加一|
|F04-T02|取消已完成物品的勾選|變為未完成，完成數量減一|
|F05-T01|重新整理已勾選清單|原勾選狀態保留|
|F05-T02|按「開始新一次準備」並確認|物品不變、勾選全部重設，其他線上成員同步看到結果|

### F06 / F07 / F09 — 共享、同步、刪除

|測試編號|操作|預期結果|
|-|-|-|
|F06-T01|Owner 產生邀請碼；另一帳號登入後正確使用|該帳號成為清單成員並能查看與編輯物品|
|F06-T02|未登入或未被授權的人存取清單|存取遭拒；不洩漏私人內容|
|F06-T03|輸入無效、已使用或遭停用的邀請碼|不加入清單並顯示提示|
|F07-T01|A 勾選尿布|B 在網頁開啟且網路正常時，不重新整理即可看到已完成|
|F07-T02|A 勾選尿布、B 勾選水壺|兩個更新皆保留，雙方最終看到兩項完成|
|F07-T03|A、B 對同一物品送出相反狀態|以最後成功寫入的結果為準，兩個裝置最終一致|
|F07-T04|A 刪除清單；B 正停留在此清單|B 自動得知清單不可用，顯示提示；點擊「確定」後返回清單列表|
|F07-T05|A 先刪除清單；B 隨後送出物品操作|B 的操作不可成功寫入已刪除的清單；顯示提示，點擊「確定」後返回列表|
|F07-T06|B 的物品操作先成功；A 隨後刪除清單|刪除完成後雙方不可再使用該清單，不留下可操作的孤立物品|
|F07-T07|B 斷網或同步連線中斷後恢復|不能誤顯示「成功儲存」；恢復後讀取資料庫最新資料|
|F09-T01|Owner 按刪除清單|必須出現確認；取消則不刪，確認才刪|
|F09-T02|Member 嘗試刪除整份清單（含直接呼叫 API）|必須遭拒|

## 7\. 非功能需求

* N01：介面能在手機與桌面瀏覽器使用，主要操作不依賴滑鼠懸停。
* N02：使用登入驗證、資料庫層級 RLS 與適當授權，保護家庭資料。
* N03：網路正常時，另一位在線上的成員應可在不重新整理的情況下取得變更；實際同步延遲會在測試階段量測，並決定合理的驗收門檻。
* N04：不支援離線寫入；若寫入未成功，要顯示失敗或未同步狀態。
* N05：斷線重連或重新開頁時，須重新取得資料庫的權威狀態，避免因漏掉事件造成畫面長期不一致。
* N06：公開部署到可供他人使用的 HTTPS 網址；程式碼上傳至 GitHub 並提供 README 操作說明。

## 8\. 預計資料實體（概念，不是最終 SQL）

|實體|用途|
|-|-|
|`auth.users`（Supabase Auth）|管理帳號驗證|
|`checklists`|清單 ID、名稱、Owner、建立時間、刪除狀態（視實作方案）|
|`checklist\_items`|物品 ID、清單 ID、物品名稱、完成狀態|
|`checklist\_members`|哪位使用者可存取哪份清單及其角色|
|`checklist\_invites`|邀請碼／邀請權限與使用狀態（或等效的安全伺服端機制）|

**技術設計備註**：Supabase Postgres Changes 的 `DELETE` 通知有權限／過濾限制。清單刪除通知的具體實作必須在 Step 05～08 選擇安全且可靠的方案，例如受授權的刪除狀態更新或私有通知；不能僅假設開放訂閱所有刪除事件即可。
